# AI Agent 的本质:从 LLM 到一个真正稳定的智能体

> 一篇试图把"agent 到底是什么"讲透的文章——它从哪来,为什么今天框架满天飞,以及一个真正稳定的 agent 到底靠什么撑起来。

---

## 一、先把本质钉死:控制流搬进了模型

如果只允许用一句话定义 agent,那就是:

**普通程序里,"下一步做什么"是程序员写死的;在 agent 里,"下一步做什么"是模型在运行时自己决定的。**

控制流(control flow)从代码里被搬进了模型。这一句话,是从"工具"到"代理"的全部分水岭,后面所有的历史、框架、稳定性问题,都是这一句话的展开。

再换两个角度补全它:

- **模型是函数,agent 是过程。** 一次 LLM 调用是 `文本进 → 文本出`,一锤子买卖,输出之后不再与世界发生关系。agent 是把这个函数塞进一个**闭环**:模型的输出变成对世界的**动作**,世界的反馈又变成模型的下一个**输入**,如此循环,直到目标达成。
- **它是"代理"而非"工具"。** "agent"这个词来自经济学的**委托—代理**关系:你委托出去的是**决策权**,不是执行。计算器是工具——你指定操作,它执行;agent 是代理——你给一个目标,它自己拆解、规划、试错、调整路径。一旦交出决策权,经典问题立刻跟来:它追求的是你的真实意图,还是某个走样的代理指标?它在你没预料到的情况下会怎么做?这就是为什么"对齐"是 agent 领域的核心议题,而不是事后补丁。

收束成一个公式:

> **agent = 模型 + 环境 + 一个闭合它们的循环。**
>
> 智能是"借"来的(来自模型本身);而 *agency*(能动性)来自"闭合这个环"——让模型的决定真的能作用于世界,也让世界的后果回到模型。模型负责"想",循环让"想"变得有后果、并把后果再喂回来。

理解了这个公式,就能理解后面的一切:历史是"如何把这个环闭合起来",框架是"如何把这个环工程化",而稳定性是"如何让这个环不发散"。

---

## 二、缺口:LLM 很会"说",但不会"做"

2020 年的 GPT-3、2022 年底的 ChatGPT,让世界第一次见识到一个能流畅处理语言的大模型。但一个**裸的 LLM**,本质上是一个被冻结的函数:给它一段文本,它返回一段文本,仅此而已。它有三个根本性的缺口:

1. **没有行动能力。** 它能写出"我应该去查一下今天的汇率",但它查不了。它的输出只是文字,不会变成真实世界里的一次 API 调用、一次文件写入、一次网页点击。
2. **没有反馈回路。** 它说完就结束了,不知道自己说得对不对,也拿不到来自环境的"地面真相"(ground truth)来纠正自己。
3. **没有持续状态。** 每次调用都从零开始,记不住上一步做了什么。

这三个缺口合起来意味着:LLM 是个绝佳的**推理引擎**,但它本身不是 agent。要把它变成 agent,你得给它装上**手**(工具/动作)、装上**眼睛**(观察/反馈)、装上**记忆**(状态),然后用一个**循环**把这一切缝起来。

接下来的整段历史,就是人们一步步把这些缺口补上的过程。

---

## 三、第一次缝合:ReAct 与工具调用(2022–2023)

补上缺口的关键一步,是 2022 年的 **ReAct** 论文(Yao 等,《ReAct: Synergizing Reasoning and Acting in Language Models》,arXiv 2210.03629,后发表于 ICLR 2023)。

在 ReAct 之前,"推理"(让模型一步步想,即思维链)和"行动"(让模型调用外部工具)被当作两件分开的事来研究。ReAct 的洞见是把它们**交错**起来,变成一个循环单元:

> **Thought(想) → Action(做) → Observation(看)→ Thought → ……**

模型先生成一段思考("我需要先查一下 X"),再生成一个动作(调用搜索工具),环境返回一个观察(搜索结果),这个观察又喂回去触发下一段思考。这个 **思考-行动-观察** 的三拍循环,就是今天几乎所有 agent 的骨架。

它为什么重要,不只是工程上的方便:

- **推理给行动提供计划和纠错能力**——模型可以根据观察更新计划、处理意外。
- **行动给推理提供地面真相**——模型不再只是凭记忆空想,而是能从环境里拉到真实信息,这显著降低了纯思维链容易产生的幻觉。

差不多同期,补缺口的另一条线也在推进:Meta 的 **Toolformer**(2023)让模型学会自己决定何时调用工具;而真正让工具调用走向工程标准的,是 **OpenAI 在 2023 年 6 月推出的 function calling**——它让"模型输出一个结构化的工具调用请求"变成 API 的一等公民,开发者终于可以稳定地把模型接到任意外部函数上。

到这里,闭环的所有零件都齐了:模型能想(推理)、能做(工具/function calling)、能看(观察反馈)。**把它们接成一个会自己转的循环,agent 就诞生了。**

---

## 四、第一波狂热与幻灭:AutoGPT / BabyAGI(2023)

零件齐了,社区立刻冲向了最激进的版本。2023 年春,**AutoGPT**(Significant Gravitas)和 **BabyAGI**(Yohei Nakajima)引爆了第一波 agent 狂热。它们的承诺极其诱人:

> 你只给一个高层目标("帮我做一份市场调研并写成报告"),agent 自己拆解成子任务,自己一轮轮执行,自己决定何时收工——一个塞进循环里的"准 AGI"。

GitHub 上一夜爆星,所有人都觉得通用自主智能体近在眼前。

然后,大部分人发现它们在真实任务上**基本跑不稳**。失败的原因,恰恰预演了后面几年整个领域要解决的全部难题:

- **误差会复合。** 循环每多转一步,最弱环节的失败概率就被乘进去一次。十几步之后,一个早期的小错会被层层放大,整条轨迹偏离到无法挽回。
- **不知道何时停。** 没有可靠的终止判据,agent 要么提前放弃,要么在子任务里无限绕圈、烧光预算。
- **上下文爆炸。** 把所有历史一股脑塞回 prompt,很快就撑爆窗口,而且越塞越乱,模型反而被噪声带偏。
- **缺乏地面真相。** 很多任务没有"测试"来告诉 agent 它做对了没有,模型只能在自己的想象里打转,错了也不自知。

这一波幻灭很重要——它把整个领域的注意力,从"模型够不够聪明",拉到了**"如何把这个会发散的循环工程化成一个可靠系统"**。后来所有的框架,本质上都是在回答这个问题。

## 五、工程化:从"链"到"图",框架为什么出现

### 5.1 第一层抽象:LangChain 与"链"

最早把这些零件打包成可复用组件的,是 **LangChain**(2022 年底)。它提供了模型封装、工具定义、prompt 模板,以及核心抽象——**链(chain)**:把若干步骤串成一条流水线,数据从头流到尾。

链的本质是 **DAG(有向无环图)**:线性、单向、从开始到结束。它非常适合**固定流程**的任务(比如"取文档 → 总结 → 翻译"),让人能快速搭起原型。

但很快人们撞上了链的天花板:**agent 的核心是"环",而链是"线"。** 一个真正的 agent 需要:

- **循环**——搜索结果不够好,就换个查询再搜一次。
- **重试与回退**——工具失败了,要能换条路、或回到上一个好状态。
- **分支**——根据中间结果决定走哪条路。
- **共享状态**——多步之间要记住做过什么、还剩什么。

这些,线性的链都很别扭。于是出现了下一层抽象。

### 5.2 关键一跃:LangGraph 与"图 / 状态机"

**LangGraph**(LangChain 团队出品,2024 年起,2025 年底发布 v1.0)就是为了补上这个缺口而生的。它把 agent 建模成一张**图**,而不是一条链:

- **节点(Node)**:一个函数——可以是一次模型调用、一次工具执行、一个规划器。它读取状态、做事、返回对状态的更新。
- **边(Edge)**:控制流——决定下一步走哪个节点,可以是有条件的(成功走这边,失败走那边)。
- **状态(State)**:一个贯穿全图的共享数据结构,每个节点读它、写它,用来记录历史、计数、中间结果。

与只支持 DAG 的框架最大的不同是:**LangGraph 支持环(cycle)。** 这正是 agent 的本质结构——信息要在模型和工具之间反复来回流动,直到收敛。本质上,LangGraph 把 agent 变成了一台**有限状态机**:你可以精确地设计它"如何推理、何时重试、怎样回退"。

它还顺手解决了第一波狂热里那些翻车点:

- **检查点 / 持久化(checkpointing)**:状态可以存盘,支持"时间旅行调试"——回到任意历史状态重跑。
- **持久执行(durable execution)**:长时间运行的任务中途崩了能恢复。
- **人在环(human-in-the-loop)**:用 `interrupt` 让流程暂停、等人审核或修改,再继续。
- **可观测性**:配合 LangSmith 追踪每一步、评估整条轨迹。

一句话概括这次跃迁:**从"AI 是一段序列"变成了"AI 是一个系统"。** 这也是为什么人们说,CrewAI 给你的是结构、AutoGen 给你的是灵活,而 LangGraph 给你的是**控制**。LangChain 自己 2026 年的工程报告也佐证了这条路的方向:他们把超过 60% 的生产事故归因于**状态管理**——而状态,恰恰是 LangGraph 这套"图 + 共享 State"设计的核心靶子。

## 六、今天的框架为什么"泛滥"

到 2026 年,agent 框架已经多到让人眼花。除了 LangGraph,常被并列讨论的还有 Anthropic 的 **Claude Agent SDK**、**OpenAI Agents SDK**、面向前端的 **Vercel AI SDK**,以及 **CrewAI、AutoGen、LlamaIndex、PydanticAI、MetaGPT** 等等。为什么会这样?

**第一,把环"接起来"很容易,把它"做稳"很难。** "模型 + 工具 + 循环"这个骨架,几十行代码就能搭出来,门槛极低;但要让它在生产里可靠运行,要解决状态、上下文、错误恢复、可观测性一大堆问题。于是每个团队都倾向于按自己的理解造一套——简单骨架人人会写,可靠工程各有各的主张。

**第二,它们其实在赌不同的侧重点,并不能互换:**

- **LangGraph**:要的是对状态、循环、人在环、持久执行、多智能体编排的**显式控制**,尤其适合复杂、受监管的企业场景。
- **Claude Agent SDK**:押注 Claude,要的是通往 computer use、记忆原语、prompt 缓存的最干净路径。
- **OpenAI Agents SDK**:押注 OpenAI,设计中心是多个专职 agent 之间的**任务交接(handoff)**。
- **Vercel AI SDK**:押注前端,在 React/Next.js 里做流式聊天体验是它的强项。

它们甚至常常**组合使用**——服务端用 LangGraph 编排,前端用 Vercel AI SDK 消费,中间调任意厂商的模型。

**第三,一个标准化的"手"出现了:MCP。** Anthropic 在 2024 年 11 月推出的 **Model Context Protocol(模型上下文协议)**,把"模型如何连接外部工具和数据"标准化成一个开放协议。它之于 agent,有点像 USB 之于外设——让工具生态可以跨框架复用,而不必每家各接一遍。

但在所有这些花样底下,有一条贯穿始终的分界线,值得单独拎出来讲。

---

## 七、所有框架底下的同一条分界线:task / workflow / agent

Anthropic 在《Building Effective Agents》(2024 年 12 月)里给出的分类,是目前最清晰的一把尺子。它把"智能体系统"拆成三层,核心区别只有一个——**控制流归谁**:

- **Task(任务)**:单次模型调用。"总结这段""分类那条""抽取这些字段"。两年前像魔法,今天是基础设施。成本可预测,失败模式有界。
- **Workflow(工作流)**:多次模型调用,但流程由**你**预先写死,模型只负责填空。"把邮件路由到正确队列 → 起草回复 → 对照政策检查 → 发送"。**控制流是你的。**
- **Agent(智能体)**:模型根据环境反馈,**自己**决定下一步调哪个工具。**控制流是模型的。** 你拥有的是目标和护栏,而不是每一个分支。

一句话:**工作流里,管道是你铺的;agent 里,管道是模型铺的。** 其余所有权衡,都建立在这个唯一的结构性选择之上。

这把尺子带来一条非常反直觉、但极其重要的工程纪律(Anthropic 的 Barry Zhang 在分享里反复强调):**不要什么都做成 agent。**

- agent 用灵活性换掉了可预测性。每多一个自主回合,就多一份延迟、多一份 token 成本、多一份"早期错误被放大"的风险。
- 如果一个任务你**能画出决策树**,那就把它做成 workflow,逐个节点优化——你会得到比任何 agent 都更高的准确率、更强的控制、更低的成本。
- 只有当任务**模糊到无法预先映射路径**、但你**仍能验证进度**时,agent 才值得。

什么时候 agent 才是对的选择?Anthropic 给的判据是四条同时成立:**任务足够模糊**(画不出决策树)、**价值足够高**(值得为探索烧 token)、**模型确实擅长**(否则错误会复合)、**错误可验证 / 代价可控**(有地面真相能兜底)。

**编程是几乎唯一同时满足全部四条的场景**:任务模糊、产出价值明显、前沿模型确实强、而且单元测试能验证对错。这就是为什么 agentic coding 工具今天能跑通,而大多数别的品类还在摸索。

Anthropic 还把 agent 的设计极简化成三件事:**它所处的环境(environment)、它能调的工具(tools)、定义它目标与边界的系统提示(system prompt)。** 其余的(缓存轨迹、并行调用、进度 UI)都是行为跑通之后的优化。

## 八、什么样的 agent 才算"真正稳定"

这是全文的核心。先确立一个最关键的判断:

> **能力(capability)≠ 可靠性(reliability)。**

一个很强的模型,放进长链条的循环里,照样可能频繁翻车——**不是因为它不会做,而是因为随机性在长轨迹上会漂移、并复合成失败。**

学界给出了相当硬的证据:

- **METR** 对长程任务的测量显示:前沿模型在"人类 4 分钟内能完成"的任务上成功率接近 100%,但在需要"4 小时以上"的任务上,成功率跌到 10% 以下。衡量可靠性的"50% 时长地平线"(agent 有一半概率成功的任务时长),过去几年大约每 7 个月翻一倍——在涨,但仍然有限。
- 关于失败机理,《Capable but Unreliable》(2026)用经典可靠性理论给出了解释:同一个能干的模型,会因为偶发的采样扰动,产生偏离"标准解题路径"的轨迹;一旦偏离,后续每一步都让回到正轨变得更难,**像滚雪球一样漂移到崩溃**。这正是 Perrow 的"正常事故理论"——复杂系统里,即便每个部件都合格,随机扰动也会层层复合成事故。

所以,**稳定的 agent,本质上是一个被工程化到"不让误差复合、能持续收敛"的循环。** 它由以下几条相互咬合的属性撑起来——注意它们不是清单,而是同一个目标("对抗发散")的不同侧面。

### 1. 让循环收敛,而不是发散(最核心)

这是一切的根。一个稳定 agent 的循环,必须有一种内在的"回正力":每一步都被拉回标准解题路径附近,而不是越走越偏。实现它的两大支柱是下面的 #2 和 #3——**地面真相**让它知道自己偏了,**上下文卫生**让它不被自己的历史污染。如果一个循环既看不到真实反馈、又被噪声不断污染,那它一定会发散;反之,它才有机会在有限步数内收敛到目标。

### 2. 每一步都踩在"地面真相"上(可验证性)

agent 最危险的状态,是**在真空里推理**——只凭自己的想象往下走,错了也不自知(这正是 AutoGPT 翻车的核心)。稳定的 agent 在每一步都要从环境拉到**真实反馈**:测试结果、编译器报错、工具返回值、网页截图。

这也是编程类 agent 之所以稳的根本原因:**单元测试就是地面真相**,模型写完代码,测试立刻告诉它对不对,循环因此有了收敛的锚点。反过来,凡是缺乏可验证反馈的任务,做成自主 agent 都格外危险。

### 3. 上下文工程:稳定性的头号战场

前面提到 LangChain 把 60% 以上的生产事故归因于状态/上下文,这不是偶然。来自 Chroma、Anthropic、Microsoft、Salesforce 的研究反复指向同一个结论:**token 的不断累积,是长程 agent 的首要失败模式**,且对大模型小模型一视同仁(Chroma 称之为"Context Rot",上下文腐烂)。

具体的失败有四种典型(write/select/compress/isolate 框架对应四种解药):

- **上下文污染(poisoning)**:模型早期的一个错误被留在上下文里,被后续推理当成事实,层层放大。
- **分心(distraction)**:旧的工具输出、已解决的错误、过时的决策堆在 prompt 里,占着 token 却毫无价值,把模型注意力带偏。
- **混淆(confusion)**:工具太多、描述太杂,模型选错工具。
- **冲突(clash)**:多轮累积的信息互相矛盾,比如早期记录的表单状态早已过时,模型却据此决策。

对应的工程手段是**主动管理整条 token 生命周期**,而不只是写好系统提示:

- **压缩 / 紧凑化(compaction)**:把旧的交互周期性地压成简短摘要。
- **近因截断**:只保留最近 N 步——一篇 2026 年的实证论文(《Less Context, Better Agents》)发现,在企业 ERP 报销流程里,只保留最近 5 次工具调用 + 一次摘要,反而比保留全部历史**又快又准**,因为它避免了"引用过时表单状态"这类陈旧错误。"更少的上下文,更好的 agent。"
- **锚定式会话状态**:维护一份结构化的"意图 / 决策 / 已做 / 下一步"文档,持续更新——比单纯截断更能保住长期意义。
- **子智能体隔离上下文**:Anthropic 的多智能体系统让每个子 agent 在**独立的上下文窗口**里干活,只把 1000–2000 token 的浓缩摘要交回主 agent,避免主上下文被细节淹没。

### 4. 错误恢复与持久状态

稳定 ≠ 不犯错,而是**犯错后不崩盘**。这需要:能检测到失败(工具报错、测试不过、超时),然后**重试 / 换路 / 重新规划**,而不是带着污染的状态硬往下走。配套的基础设施是**检查点与持久执行**:状态定期存盘,崩了能从最近的好状态恢复,甚至回滚到任意历史点重跑。这正是 LangGraph 这类框架把 checkpointing 做成一等公民的原因。

### 5. 明确的边界:停止条件与预算上限

发散的另一种形态是"停不下来"。稳定的 agent 必须有清晰的**终止判据**(目标达成、或确认无解),以及硬性的**预算护栏**:最大循环次数、最大 token、最大耗时、最大工具调用数。Anthropic 的经验法则给了个直观的量级感:大约 10 美分的任务预算 ≈ 3 万–5 万 token,超出这个量级还在循环,往往说明它该被设计成 workflow,而不是放任 agent 探索。

### 6. 工具设计:给 agent 用的工具,不是 API 的薄包装

Anthropic 在《Writing Effective Tools for Agents》里点明:工具是一种**新型软件——确定性系统(工具)与非确定性系统(agent)之间的契约**。一个常见错误是把现成 API 端点直接包成工具。更好的做法是:

- **少而精**:几个针对高频工作流精心设计的工具,胜过几十个零散工具(否则就是上面说的"混淆")。
- **高信噪比的返回**:别让工具吐回一大坨,让 agent 逐字读完浪费上下文;返回应当像"直接翻到通讯录的相关那一页",而不是"从头逐页扫"。
- **能合并多步**:把常被连用的几步操作合进一个工具调用。
- **用评估来打磨**:工具好不好,要靠跑评估来量化,而不是凭感觉。

### 7. 可观测性与评估:别靠"感觉"上线

agent 是非确定性的——同样的输入,不同次运行可能走出不同轨迹,这让传统调试方法直接失效。所以稳定 agent 的前提是**能被观测、能被评估**:

- **轨迹追踪**:记录每一步的思考、工具调用、返回、token 消耗、错误,出问题时能定位到"在哪一步偏的"。
- **评估驱动开发(eval-driven)**:建一套评估集,用它来量化每次改动的效果,而不是"shipping on vibes(凭感觉上线)"。
- 在多智能体系统里,还要追踪 agent 之间的**决策与交互模式**,否则协同一旦出错几乎无从排查。

### 8. 最小自主原则:能不给的自主权就别给

这条把整篇文章收口。**最稳定的 agent,往往是那个"在能解决任务的前提下,自主性最低"的设计。** 凡是你能画出路径的部分,就做成 workflow;只在真正无法预先映射、但仍可验证的地方,才交出控制权给模型。给模型的 agency,应当**刚好等于任务所需**,多一分都是在给发散和成本买单。

把这八条压成一句话:

> **稳定的 agent,是一个被工程化的循环——每一步都踩在地面真相上、上下文保持干净、错误能被捕获而不复合、整个系统可观测可评估、并且自主权被收敛到任务真正需要的最小程度。** 模型负责聪明,这套工程负责让聪明不发散。

---

## 九、回到本质,以及往哪走

绕了一大圈,我们回到最初那个公式:

> **agent = 模型 + 环境 + 一个闭合它们的循环。智能是借来的,agency 是工程出来的。**

整部历史就是这个公式的展开:**ReAct** 第一次把环闭合,**AutoGPT** 用一次惨痛的狂热证明了"闭合容易、收敛难",**LangChain → LangGraph** 把环从"线"做成了可控的"图 / 状态机",**MCP 和各家 SDK** 把环的零件标准化、产品化,而**上下文工程、评估、可观测性、最小自主**这一整套,则是在回答那个从 2023 年就悬而未决的问题:**怎么让这个会发散的环,变成一个可靠的系统。**

往前看,趋势也清晰:衡量可靠性的"时长地平线"还在每 7 个月左右翻一倍;研究的重心正从"训练更聪明的模型",转向"在运行时把这个循环管得更好"——运行时基础设施、执行期的安全与纠偏、长程可靠性,正在成为新的主战场。

所以,如果只带走一句话:

> **判断一个 agent 好不好,别问它的模型有多聪明,要问它的循环有多稳——它能不能在每一步踩到真相、把上下文管干净、把错误挡在复合之前,并且只在真正需要的地方,才把方向盘交给模型。**

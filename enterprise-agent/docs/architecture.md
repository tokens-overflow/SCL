# 架构说明：六层与六个组件

## 一、为什么是六层

分层最实际的用处，是**决定新写的代码该放哪儿**。

| 层 | 只回答一个问题 | 目录 | 典型失效表现 |
|----|--------------|------|------------|
| 入口层 | 任务怎么进入系统 | `app/api/` | 只做聊天入口，采纳率上不去 |
| 认知层 | 理解意图并提出方案 | `app/cognitive/` `app/llm/` `app/context/` | 答非所问、引用不存在的资料 |
| 控制层 | 判断能不能做 | `app/control/` | 越权、绕过审批 |
| 行动层 | 真正执行动作 | `app/actions/` | 副作用没做幂等 |
| 状态层 | 可恢复的施工记录 | `app/state/` | 重启后整单重来 |
| 运营层 | 保证长期稳定运行 | `app/operations/` | 「哪里变了没人说得清」 |

**失效比定义更值得记**——线上出问题时你是先看到现象，再回头找层的。

## 二、六层不是一条直线

四层是主链路，另外两层横向贯穿：

```
入口层 → 认知层 → 控制层 → 行动层     （纵向主链路）
  ↓        ↓        ↓        ↓
──────────── 状态层 ────────────      （在链路【下面】）
──────────── 运营层 ────────────      （在链路【旁边】）
```

### 为什么状态层必须是横向的

如果把状态层做成链路上的一环（「执行完再统一写状态」），那么
**进程在执行和写状态之间崩溃，这次执行就成了无人知晓的孤儿**——
外部系统那边已经生效，你的库里查无此事。

正确做法：

1. **执行前先登记意图**（状态置 RUNNING，带幂等键）
2. **执行后再落盘结果**
3. 两者中间挂掉 → 恢复时看到一条 RUNNING 的悬挂记录 →
   **拿幂等键去外部系统对账**就能查明真相

本项目的落点：`ActionExecutor.execute()` 里 `reserve()` 一定在
`tool.execute()` 之前调用。

### 为什么运营层也是横向的

如果只在任务成功时才写日志，那么**最需要排查的失败路径反而什么都没留下**。

本项目的落点：`AuditService` 在每个分支上都写事件，包括 DENY、TIMEOUT、
补偿失败、非法状态转换。

## 三、依赖方向

严格单向，不允许反向依赖：

```
core（枚举/异常/配置/ID）
  ↑
security（身份/密钥/净化）
  ↑
context（Context/Memory/RAG）
  ↑
llm（Provider 抽象）        state（ORM/仓库）
  ↑                            ↑
cognitive（意图/规划）      runtime.models（领域模型）
  ↑                            ↑
control（策略引擎）  ←──  actions（工具/执行器/补偿）
  ↑                            ↑
        runtime（编排/状态机/恢复/调度）
                  ↑
                api（路由）
```

几条刻意的安排：

- **枚举全部收在 `core`**：状态层、控制层、行动层、运营层都要引用它们，
  散落在各自模块里会立刻产生循环依赖。
- **`runtime/models.py` 与 ORM 平行**：ORM 对象绑定 Session，脱离 session
  访问未加载属性在异步下会直接 `MissingGreenlet`。领域模型是纯数据。
- **`llm` 不依赖 `control`**：模型层永远不知道有权限这回事。
- **`actions/base.py` 不依赖 `state`**：所以工具可以被单独测试，不用连数据库。

## 四、六个核心组件

六层是职责划分，六个组件是实现这些职责的东西。**它们不是一一对应的**。

| 组件 | 关键理解 | 做砸的表现 |
|------|---------|-----------|
| LLM | 是认知组件，不是最终裁判 | 意图识别错，后面全歪 |
| Context | 桌面上摊开的材料，不等于全部长期记忆 | 给少了就猜；给多了关键项被淹没，成本还翻倍 |
| Tools | 模型只提出 Tool Call，是否执行由控制层决定 | 粒度失衡；写操作没做幂等 |
| State | 不能只存在模型上下文里 | 重复执行、丢步骤、无法恢复 |
| Control | 模型提出建议，Control 决定是否允许 | 越权与超额执行——损失最大的一类 |
| Runtime | 整个系统真正的流程主控 | 成本失控、故障无法定位、任务悬挂无人管 |

### Runtime 是最容易被忽略的那个

讲 Agent 的文章大多把篇幅给了 LLM、Context 和 Tools，因为它们最像「AI」。
但真正决定系统能不能上线的是 Runtime——
**它是那个在凌晨三点把挂掉的任务捡起来接着跑的东西。**

## 五、两类决策的分界线

| 认知决策 · 交给模型 | 执行决策 · 交给程序 |
|-------------------|-------------------|
| 没有唯一正确答案 | 有唯一正确答案 |
| 用户到底想做什么 | 这个用户有没有权限 |
| 任务应该怎么拆 | 参数是否合法 |
| 哪个工具可能合适 | 是否需要审批 |
| 结果该怎么向人解释 | 是否可以重试 / 补偿 / 从哪步恢复 |

**判据**：

1. 这个问题的正确答案唯一吗？唯一 → 程序。
2. 出错之后要有人负责吗？要 → 程序。

### 还有一层成本原因

每问一次模型，都要把整个上下文重新喂一遍。而上下文会随步数越来越长，
所以**一次任务里模型调用的次数，几乎直接决定了它的成本和延迟**。

API 超时了要不要重试、重试几次、读任务状态、检查幂等键、判断该从第几步恢复——
这些都有确定答案，写死在代码里既更可靠也更便宜。
**把它们交给模型，是花钱买不确定性。**

本项目的落点：完整折扣流程里模型只出现两次（解析意图、生成回复），
`resume_task()` 里一次都没有。测试 `test_restart_resumes_from_correct_step`
显式断言了这一点。

## 六、嵌套 Agent 的对外契约

复杂 Agent 内部往往有自己的一整套 LLM、工具、状态机和子工作流。
上层编排器不该也不需要知道这些。

```python
class AgentResult(BaseModel):
    agent_id: str
    task_id: str
    status: str              # SUCCESS / FAILED / TIMEOUT / PARTIAL_SUCCESS / WAITING_APPROVAL
    result: dict | None
    error_code: str | None
    retryable: bool          # ← 编排必需的第六个字段
    idempotency_key: str | None
    external_reference_id: str | None
    cost: dict               # ← 运营层要的
    trace_id: str            # ← 少了它没法跨 Agent 串链路
    elapsed_ms: int
```

**契约里最重要的字段是 `retryable`，而且它必须由被调方声明。**

只有 Agent 自己知道「文档缺失」是重试也没用（要人补材料），
而「向量库连接失败」重试就能好。上层编排器如果靠错误码字符串去猜，
被调方一改文案就全乱套——这是嵌套编排里最常见的一种耦合。

### 一个实际好处

契约稳定之后，**子 Agent 可以被替换成一段纯代码，上层完全无感**。
很多「Agent」在业务跑顺之后会发现根本不需要模型——规则就够了。
有统一契约的话，这种降级是无痛的。

本项目的 `DiscountRecommendationAgent` 就是纯规则实现，
`FunctionAgentWorker` 演示了把普通函数包成 Agent。

## 七、什么时候真的需要多 Agent

合理的理由只有四个：

1. 不同角色需要不同的工具权限边界
2. 上下文互相污染必须隔离
3. 不同子任务的成本差异大到该分开
4. 有明确的并行加速收益

如果单 Agent 挂几个工具就能做，拆开只是把误差复合的链路又拉长了一截，
还多了一套状态同步要维护。

### 两个容易忽略的账

- **延迟账**：并行五个 Agent，总耗时不是平均值而是**最大值**。
  所以必须给每个槽位设独立超时，并想清楚「超时的那个能不能丢」。
- **成本账**：五个 Agent 各自带完整上下文，成本大致是单 Agent 的
  **五倍以上**（不是五分之一）。拆分要有明确收益，不能只为了「架构看起来高级」。

## 八、与 LangGraph 等框架的关系

核心工程**不依赖** LangGraph。`app/examples/langgraph_adapter.py` 提供了
可选的适配示例，其中最重要的一张对照表：

| 本项目 | LangGraph 对应物 | 说明 |
|--------|-----------------|------|
| `Orchestrator._drive()` | StateGraph 执行循环 | 流程推进 |
| `TaskStateMachine` | 节点与边 | 我们的迁移表是显式断言 |
| `task_steps` 表 | Checkpointer | **不能互相替代**：对账要幂等键和外部凭证 |
| `PolicyEngine` | （无对应物） | 权限/业务规则/审批必须自己实现 |
| `ActionExecutor` | （无对应物） | 框架不会替你做幂等和对账 |
| `RecoveryService` | 部分对应 Checkpointer | 「悬挂步骤对账」仍需自己写 |

**结论**：编排框架能省的是流程推进的样板代码，
省不掉控制层、幂等和对账——那些正是「企业级」这三个字的实际内容。

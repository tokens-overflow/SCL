# 可靠性：幂等、超时、补偿、断点续跑

这四件事是一套的：
**幂等让重试安全，补偿让失败可收场，续跑让两者能在崩溃之后继续生效。**

## 一、超时：结果未知，不等于失败

请求超时了，真实情况可能是三种中的任意一种：

1. 请求根本没到达对方，**没有执行**
2. 已经执行成功，**只是响应没回来**
3. 对方还在处理中，**稍后会成功**

### 两种都会出事的错误处置

| 错误处置 | 后果 |
|---------|------|
| 当成功处理 | 如果其实没执行，你的库里记着「已完成」，钱却还在。用户来投诉时你还查不出问题。 |
| 当失败处理并回滚 | 如果其实已经执行了，你凭空少了一笔，而且回滚动作本身可能又制造一次不一致。**这是超时误判里代价最高的一种。** |

### 唯一正确的处置

落成 `TIMEOUT` / `UNKNOWN`，进对账队列，拿幂等键 / 业务单号 / 状态查询接口
去问外部系统真实结果。

```python
# app/actions/base.py
async def query_external_status(self, idempotency_key, execution_context):
    """所有写工具都必须实现这个方法。

    * 查到已成功 → SUCCESS + external_reference_id，只补写状态，不重复执行
    * 确认未发生 → FAILED + retryable=True，可带同一幂等键安全重试
    * 查无可查   → None，升级人工（【绝不猜】）
    """
```

**对账不是一次性的**：外部系统可能「稍后会成功」，所以真实实现应该
带退避地查几轮，仍不明确才升级人工。（本项目 Demo 只查一轮，已在 README 限制中标注。）

### 关键实现细节：把对账结果写回去重记录

对账查明真相之后，**必须把结果写回 `tool_executions` 表**。

去重记录里此刻存的还是「TIMEOUT / IN_FLIGHT」——也就是「我不知道」。
如果不更新它，下一次重试调用 `reserve()` 时会再次命中这条未决记录，
被当作「结果未知」直接返回，于是重试永远执行不下去，
最后耗尽重试次数变成一个**假的失败**。

换个角度说：去重表记录的是**外部副作用的真相**。
对账的全部意义就是把「不知道」变成「知道」，那就必须把这个「知道」落回表里。

代码：`app/actions/executor.py::reconcile()`

## 二、幂等

### 键要按「动作」生成，不是按「请求」

普通接口用请求 ID 做幂等键就够了。但在 Agent 里，
模型可能在第 3 步和第 7 步提出**同一个动作**（它忘了自己做过）。
这是两个不同的请求、不同的时间戳——用请求 ID 会被判为两笔，真的执行两次。

```python
def build_idempotency_key(task_id, step_name, tool_name, arguments, suffix=None):
    raw = f"{task_id}|{step_name}|{tool_name}|{canonical_json(arguments)}"
    ...
```

### 参数归一化必须做三件事

否则「同一个动作」会因格式差异被算成两个：

| 规则 | 例子 |
|------|------|
| 键排序 | `{"a":1,"b":2}` ≡ `{"b":2,"a":1}` |
| 数字归一 | `328` ≡ `328.00` ≡ `Decimal("328.000")` |
| 字符串 trim | `" C001 "` ≡ `"C001"` |

反过来，`{"a": None}` 与 `{}` **不能**合并——语义不同。

### 顺序很重要：先占位，再执行

很多实现把「写去重记录」放在执行成功之后。这留了一个致命窗口：
**如果在「执行成功」和「写记录」之间进程崩了，去重记录就丢了，
重试必然产生第二笔。**

正确顺序：

```
1. reserve()          → 写 IN_FLIGHT 记录（执行前占位）
2. tool.execute()     → 真正执行
3. complete()         → 改成 SUCCESS / FAILED / TIMEOUT
```

### 四种幂等命中的处理

| 已有记录状态 | 处理 |
|------------|------|
| SUCCESS / SKIPPED_IDEMPOTENT | **直接返回历史结果，不重复执行** |
| IN_FLIGHT | 返回 UNKNOWN → 走对账（可能有另一个 worker 在跑，也可能上次崩在中途） |
| TIMEOUT / UNKNOWN | 返回未决状态 → 走对账 |
| FAILED | 允许按重试策略重新执行 |

### 同一幂等键但参数不同 → 必须拒绝

如果返回旧结果，**第二笔业务会被静默吞掉**，而没有任何人知道。

```python
raise IdempotencyConflictError("同一幂等键对应的参数不一致，拒绝执行")
```

### 数据库唯一约束是最后一道闸

应用层的「先查再写」在并发下是不够的——两个进程会同时查到「没有」然后同时写入。

```python
UniqueConstraint("idempotency_key", name="uq_execution_idempotency_key")
```

## 三、重试

### 可重试白名单，不是黑名单

**未知错误默认不重试**比「未知错误默认重试」安全得多——
对写操作来说，多重试一次可能就是多扣一笔钱。

```python
RETRYABLE_ERROR_CODES = {UPSTREAM_UNAVAILABLE, RATE_LIMITED, NETWORK_ERROR, INTERNAL_ERROR}
```

`TIMEOUT` 和 `UNKNOWN_EXECUTION_STATE` **不在其中**：它们必须先对账。

### retryable 由被调方声明

只有工具自己知道这次失败的性质。上层靠错误码字符串去猜，
被调方一改文案就全乱套。

判定优先级：

1. **未知状态优先** → 不重试（覆盖后面所有判断）
2. 次数用尽 → 不重试
3. 被调方明确说不可重试 → 不重试
4. 错误码白名单 → 重试
5. 其余 → 不重试

### 退避 + 抖动

没有抖动的话，同时失败的一批任务会在同一毫秒一起重试，
形成重试风暴把刚缓过来的下游再次打挂。**抖动是必需的，不是可选的。**

有 `Retry-After` 时优先用它——下游最清楚自己什么时候能缓过来。

### 重试状态必须持久化

`retry_count` 和 `next_retry_at` 都要落库。
只在内存里维护重试计划意味着进程一重启就失忆，
**而进程重启正是最需要它的时刻**。

### 为什么不用 tenacity

tenacity 的模型是**进程内的循环重试**——进程一挂，重试计划就没了。
企业级场景里，重试必须能跨进程重启存活，所以要自己实现并落库。

## 四、补偿

### 数据库事务回滚 ≠ 业务补偿

| | 事务回滚 | 业务补偿 |
|--|---------|---------|
| 撤销什么 | 我们自己事务里、**还没提交**的写入 | **已经提交、已经对外生效**的业务动作 |
| 谁保证 | 数据库 | 你自己写的反向业务动作 |
| 会失败吗 | 不会 | **会** |
| 有状态吗 | 没有 | 有独立状态、独立幂等键、独立审计 |

把两者混为一谈的后果非常具体：你写了 `try/except: session.rollback()`，
以为「出错了就撤销」，但外部系统那笔折扣已经生效了，rollback 对它毫无作用。
**库里干干净净，客户那边白拿了一个折扣，而且没有任何记录。**

### 补偿的三条纪律

1. **补偿动作本身必须幂等。** 补偿也会失败、也会重试，它不比正向动作安全。
   本项目用原键 + `:comp` 后缀作为补偿的独立幂等键。

2. **不可补偿的动作排在链路最后。** 发通知、发短信、对外公告这类收不回的
   动作放前面，后面任何一步失败你都收不了场。
   本项目的 `Planner._normalize()` **由程序强制重排**，不依赖模型自觉。

3. **补偿不给模型调用权。** 它由 Runtime 在失败路径上调用。
   让模型能自由触发「撤销」，等于给了它一把可以来回拨的开关。

### 逆序执行

```
冻结预算  SUCCESS  ┐
创建采购单 SUCCESS  ├─→ 提交订单 FAILED
                   ┘
补偿顺序：取消采购单 → 释放预算   （后做的先撤）
```

反过来先释放预算，采购单就成了没有预算支撑的孤儿单据。

### 不可补偿要如实声明

```python
class SendNotificationTool(AgentTool):
    supports_compensation = False   # 已发出的短信收不回来
    # compensate() 刻意不实现，继承基类的 NotImplementedError
```

**假装能补偿**（比如发一条「上一条作废」的短信）会让上层误以为链路是
可回滚的，从而把它排到链路中间——那才是真正的坑。

补偿失败或存在不可补偿动作时，任务落 **MANUAL_REVIEW 而不是 FAILED**：
FAILED 意味着「已经收场了」，但这里明明还有东西没收拾干净。

### 关于「恰好一次」

分布式系统里不存在恰好一次。能真正做到的是
**「至多一次副作用 + 可判定的最终状态」**：

- 每个副作用带幂等键 → 保证不重复
- 每个任务有明确终态 → 保证不会悬着

**没有终态的任务，比失败的任务更麻烦**——因为没人知道它还在不在跑。

## 五、断点续跑

```python
async def resume_task(task_id: str) -> AgentTask: ...
```

算法（**整个过程一次模型调用都没有**）：

1. 按 `task_id` 读出任务与全部步骤
2. 已 SUCCESS 的步骤**直接跳过**
3. RUNNING 但超过 `STALE_RUNNING_SECONDS` 无更新 → 标记 **UNKNOWN**（不是 FAILED）
4. TIMEOUT / UNKNOWN 的写操作 → **对账**
5. 只读步骤无副作用 → 直接重试，不需要对账
6. 可重试 → 按退避计划重试
7. 不可重试 → FAILED 或 MANUAL_REVIEW
8. WAITING_APPROVAL → 检查审批结果，没批就继续等
9. 需要补偿 → 逆序补偿
10. 从正确的步骤继续

### 为什么不能依赖模型记忆

模型的「记忆」是上下文窗口里的文本。它会被截断、会过期、
会因为一次对话重置而清零。而且它对「我上次到底有没有执行成功」
这个问题的回答本质上是**生成**，不是**读取**——
模型会流畅地告诉你一个听起来很合理的答案，而那个答案可能是错的。

状态表不会。`SELECT * FROM task_steps WHERE task_id = ?`，每次读出来都一样。

测试 `test_restart_resumes_from_correct_step` 显式断言了
「恢复过程不增加模型调用」。

### 一个额外好处

同一套状态机既支持**崩溃恢复**，也支持**人工审批挂起**——
两者本质上是同一件事：**把任务冻在某一步，等外部条件满足后再继续。**

所以做好了断点续跑，Human-in-the-Loop 几乎是白送的。

## 六、部分成功

「折扣成功但通知失败」是一个**正常的业务结局**，不是失败。

处理原则：

- 关键步骤（`critical=True`）全部成功 + 可选步骤有失败 → `PARTIAL_SUCCESS`
- **绝不因为通知失败去撤销折扣**——那是两回事
- 通知可以单独重试
- 「是否撤销折扣」必须由明确业务规则或人工决定，**不能由模型擅自决定**

代码：`Orchestrator._finalize()`，测试 `test_discount_succeeds_notification_fails`。

## 七、多 Agent 的聚合规则

拿到五个子 Agent 的结果之后怎么办，**是配置，不是模型的临时判断**：

```python
AggregationRule(
    required=["customer_eligibility_agent"],   # 失败 → 整单必须停
    min_success=1,                             # 其余至少 N 个成功
    retry_on=["TIMEOUT"],                      # UNKNOWN 不在其中：要先对账
    max_retry=1,
    human_review_if=lambda rs: 高风险结论,
    slot_timeout_seconds=10.0,                 # 【必须有】并行总耗时 = 最慢的那个
)
```

**必需项必须显式声明**，否则「合同风险没跑出来」会被当成「没有风险」——
这是多 Agent 编排里最贵的一类错误。

**跳过 ≠ 成功**：把 SKIPPED 记成 SUCCESS 会让 `min_success` 算错。
